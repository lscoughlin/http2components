The send-loop review found a separate ownership race. Normal loop exit
cleared the send-owner flag under its lock, and the outer cleanup cleared
it again. A new sender could acquire the flag between those actions.
The old cleanup could then erase the new claim. Commit `1cc299b` makes
cleanup release only its own claim. The old diagnostic counter covered
the whole call through cleanup, so its overlap message also counted calls
that crossed a normal handoff. It was not proof of simultaneous active
drains. The repaired ownership trace kept one owner, but the integration
timeout remained.

A later trace located the stalled request bodies. Four uploads started
together. One completed its body at once; three completed only after the
three-second deadline. The first two server handlers waited for those

wake path signals one shared auto-reset event once per waiting sender.
Those repeated signals can combine before a sender consumes them. A
trace recorded four waiting senders and an initial wake that released only
two promptly. This behavior depends on scheduling. The per-waiter event
repair is commit `84021f2`. A corrected threaded Linux control issued four
signals before waiting: only the first wait returned at once, and the next

limit was 64. After one completed warm-up connection, the first wave of 64

Both waves were observed before the configured 1,000 ms handshake timeout.

The configuration reached the factory, and the probe confirmed that the
first wave remained open before starting the excess wave. The accepted
observer runs after the dependency admission gate. This evidence indicates
active excess admission, not a cumulative count of sockets already refused.
The test stopped before classifying the excess peer closures; their final
cleanup rows do not prove that the server closed them.

The dependency checks the polled socket count and pending-read count
separately. The repaired implementation reserves one slot before a connection
enters either set and releases it on close or failed creation. The probe also
requires observed server closure, reset, or TCP refusal for each excess peer
within its existing 200 ms observation. An open excess socket is a failure.
The connection-load, combined WebSocket/SSE, and million-request TLS stages
did not run after the failed first stage.

The strict negative control on the old implementation failed all four cases.
